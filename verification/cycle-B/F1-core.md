### Finding B1-01 (critical) Presolve integer-bound rounding drifts outward at |bound| >= ~1e9; B&B and Automatic report .optimal infeasible points
- claim: Presolve.swift:13 and README §2.2 "rounds integer bounds"; Presolve.swift rule 6 comment "round fractional bounds inward"; BranchAndBound.swift:193 "integer bounds rounded inward"; .optimal promises a feasible proven solution (Status.swift).
- observed: integer x with integral bounds [1.7e9, 1.7e9+100], minimize x -> BranchAndBound()/Automatic() status .optimal, x = 1699999989 (11 below the lower bound); CompiledLP.maxViolation(at:) at the reported point = (bounds 11.0, rows 0). DSL model start (integer, >= 1_700_000_000), finish >= start + 3600, min finish -> optimal start=1699999989, finish=1700003589 (expected 1700000000/1700003600). x>=2e9 -> violation 22; x>=1e10 -> 110; x>=1e12+0.5 -> 10999.5; maximize side drifts upward symmetrically. Presolve.run(mode: .boundsOnly) alone maps xl=1e9+0.5 to 999999990.
- why wrong: normalizeBounds computes ceil(xl - 1e-9*max(1,|xl|)). For |xl| >= ~1e9 the slack is >= 1 unit, so an integral bound is lowered by one or more units; the change sets `changed`, the next pass rounds the new value again, and so on for up to 10 passes plus the final normalize: 11 steps of 1e-9*|b| each. The rule loosens bounds instead of tightening them, and B&B adopts pre.reduced as its problem with no check of the incumbent against the original bounds.
- location: Sources/ZTronLPCore/Model/Presolve.swift:139-150 (normalizeBounds), :166 (pass loop re-applying it), Sources/ZTronLPBranchAndBound/BranchAndBound.swift:199-202 (uses pre.reduced as the problem).
